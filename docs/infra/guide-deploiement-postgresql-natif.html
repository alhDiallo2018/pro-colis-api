Guide de déploiement · Infrastructure

Déployer PRO COLIS, de bout en bout.

Guide d’installation et d’exploitation du domaine, de Caddy, des conteneurs Web/API, des uploads et de PostgreSQL 16 natif sur un VPS Debian.

HTTPS automatique API et Web conteneurisés PostgreSQL natif Rollback documenté
00 / CIBLE

Une seule entrée publique, des responsabilités nettes

Caddy est le seul service exposé. Il sert la SPA React et reverse-proxy l’API Express. PostgreSQL est géré par Debian et joint depuis l’API par un socket Unix monté dans le conteneur.

Avant

Architecture historique

  • Conteneurs Caddy, API et PostgreSQL
  • Base dans le volume postgres-data
  • API → DNS Docker postgres:5432
  • Cycle de vie de la base lié à Compose
→
Après

Architecture de production cible

  • Conteneurs Caddy et API uniquement
  • PostgreSQL 16/main piloté par systemd
  • API → socket /var/run/postgresql
  • Données DB hors du cycle de vie Docker
Internet → Caddy :80/:443 → SPA / API :8080 → socket Unix → PostgreSQL 16

Routage et persistance

Composant Responsabilité Exposition / persistance
Caddy TLS, SPA, compression et reverse-proxy Ports 80/443, volumes caddy-data et caddy-config
API Express /api/*, /uploads/* et IPN PayDunya Réseau Compose uniquement, volume api-uploads
PostgreSQL 16 Données métier et migrations Prisma Socket Unix uniquement, données dans /var/lib/postgresql/16/main
!

Ne jamais copier le contenu brut du volume Docker. Le passage d’une image Alpine à une installation Debian doit être réalisé avec un dump logique pg_dump puis pg_restore.

01 / RÉSEAU

Préparer le DNS et les ports publics

Le domaine principal et, si utilisé, le sous-domaine www doivent pointer vers l’IP publique du VPS avant le premier démarrage de Caddy.

TypeNomValeurUsage
A sendprocolis.exemple.com IP_PUBLIQUE_DU_VPS Domaine principal
A ou CNAME www.sendprocolis.exemple.com IP du VPS ou domaine principal Redirection www → domaine principal
Shell · contrôles DNS
dig +short sendprocolis.exemple.com A
dig +short www.sendprocolis.exemple.com A

sudo ss -ltnp | grep -E ':(80|443)\b' || true
!

Let’s Encrypt ne pourra pas émettre le certificat si le DNS n’est pas propagé ou si les ports 80 et 443 sont filtrés. Le port 5432 ne doit jamais être ouvert sur Internet.

02 / DEBIAN

Préparer un VPS Debian

Installer Docker depuis son dépôt officiel, activer Compose et limiter le pare-feu à SSH, HTTP et HTTPS. PostgreSQL 16 sera installé séparément dans la section Base native.

Shell · Docker Engine et Compose
sudo apt-get update
sudo apt-get install -y ca-certificates curl git ufw

sudo install -m 0755 -d /etc/apt/keyrings
sudo curl -fsSL https://download.docker.com/linux/debian/gpg \
  -o /etc/apt/keyrings/docker.asc
sudo chmod a+r /etc/apt/keyrings/docker.asc

echo "deb [arch=$(dpkg --print-architecture) signed-by=/etc/apt/keyrings/docker.asc] \
https://download.docker.com/linux/debian \
$(. /etc/os-release && echo "$VERSION_CODENAME") stable" \
  | sudo tee /etc/apt/sources.list.d/docker.list > /dev/null

sudo apt-get update
sudo apt-get install -y \
  docker-ce \
  docker-ce-cli \
  containerd.io \
  docker-buildx-plugin \
  docker-compose-plugin

sudo usermod -aG docker "$USER"

Se déconnecter puis se reconnecter afin que le groupe Docker soit pris en compte.

Shell · pare-feu
# Toujours autoriser SSH avant d'activer UFW.
sudo ufw allow 22/tcp
sudo ufw allow 80/tcp
sudo ufw allow 443/tcp
sudo ufw deny 5432/tcp
sudo ufw --force enable

sudo ufw status verbose
docker --version
docker compose version
!

Vérifier le port SSH réel avant ufw enable. Si SSH écoute sur un autre port, autoriser ce port à la place de 22/tcp afin de ne pas verrouiller le VPS.

05 / CONTRÔLES

Valider le VPS avant la migration

Exécuter les commandes depuis la racine du projet sur le VPS. Une fenêtre de maintenance est nécessaire pour garantir qu’aucune écriture ne survient entre le dump et la bascule.

  • Accès SSH avec un utilisateur membre du groupe Docker et autorisé à utiliser sudo.
  • Conteneur source identifié : procolis-node-postgres ou sendprocolis-postgres selon l’ancienne stack.
  • Espace disque disponible pour au moins deux dumps complets et la base restaurée.
  • Mot de passe PostgreSQL fort stocké dans un gestionnaire de secrets.
  • Maintenance annoncée et procédure de rollback connue par l’opérateur.

État initial

Shell · inventaire
cd ~/procolis/SendProColis-Api

docker compose ps

docker exec procolis-node-postgres \
  psql -U procolis -d procolis \
  -c "SELECT version();"

sudo ss -ltnp | grep ':5432' || true
command -v pg_lsclusters >/dev/null && pg_lsclusters || true
?

Si le port 5432 est déjà occupé, identifier le processus ou le cluster avant de continuer. Ne pas installer un second cluster sur un port choisi implicitement.

i

Les commandes de migration ci-dessous utilisent la source historique procolis-node-postgres, l’utilisateur procolis et la base procolis. Si l’ancienne production utilise les noms sendprocolis-*, résoudre d’abord les valeurs exactes avec docker inspect et les substituer partout de manière cohérente.

06 / BACKUP

Sauvegarder avant toute modification

Les dumps sont stockés hors du dépôt afin qu’ils ne soient jamais ajoutés à Git ni inclus dans l’image par le COPY . . du Dockerfile.

Shell · répertoire privé
BACKUP_DIR=/var/backups/procolis

sudo install -d \
  -m 700 \
  -o "$(id -un)" \
  -g "$(id -gn)" \
  "$BACKUP_DIR"

PRE_BACKUP="$BACKUP_DIR/procolis-preflight-$(date +%Y%m%d-%H%M%S).dump"
Shell · dump custom et contrôle
docker exec procolis-node-postgres \
  pg_dump -U procolis -d procolis \
  --format=custom \
  --verbose \
  > "$PRE_BACKUP"

test -s "$PRE_BACKUP"

docker exec -i procolis-node-postgres \
  pg_restore --list \
  < "$PRE_BACKUP" \
  > /dev/null

chmod 600 "$PRE_BACKUP"
sha256sum "$PRE_BACKUP"
du -h "$PRE_BACKUP"
✓

Continuer uniquement si le fichier est non vide, si pg_restore --list se termine sans erreur et si sa somme SHA-256 a été conservée.

07 / POSTGRES

Installer PostgreSQL 16 nativement

La version majeure cible reste 16, identique à celle de l’image source. Le dépôt PGDG fournit une version précise et les mises à jour de maintenance associées.

Shell · installation PGDG
sudo apt update
sudo apt install -y postgresql-common

sudo /usr/share/postgresql-common/pgdg/apt.postgresql.org.sh

sudo apt update
sudo apt install -y postgresql-16 postgresql-client-16

sudo systemctl enable --now postgresql
Shell · santé du cluster
sudo systemctl status postgresql --no-pager
pg_lsclusters

sudo -u postgres psql -Atqc \
  "SELECT current_setting('server_version');"

Le cluster attendu est 16/main, port 5432, statut online.

08 / ACCÈS

Créer le rôle et protéger le socket

Le rôle applicatif n’est ni super-utilisateur, ni créateur de rôles ou de bases. Son accès au socket local exige une authentification SCRAM-SHA-256.

Mot de passe

Générer un secret compatible avec une URL sans encodage supplémentaire :

Shell
openssl rand -hex 32

Le stocker immédiatement dans le gestionnaire de secrets.

Rôle et base

Shell
sudo -u postgres createuser \
  --pwprompt \
  --no-superuser \
  --no-createdb \
  --no-createrole \
  procolis

sudo -u postgres createdb \
  --owner=procolis \
  --template=template0 \
  --encoding=UTF8 \
  procolis

Règle pg_hba.conf

Localiser le fichier réellement chargé :

Shell
sudo -u postgres psql -Atqc "SHOW hba_file;"

Ajouter la règle suivante avant la règle générique local all all peer :

pg_hba.conf
# L'API PRO COLIS utilise le socket PostgreSQL monté dans son conteneur.
# SCRAM impose l'utilisation du mot de passe fort du rôle applicatif.
local   procolis   procolis   scram-sha-256
Shell · recharger et tester
sudo systemctl reload postgresql

sudo -u postgres psql -x -c "
SELECT line_number, type, database, user_name, auth_method, error
FROM pg_hba_file_rules
WHERE error IS NOT NULL;
"

psql \
  'postgresql://procolis@localhost/procolis?host=/var/run/postgresql/' \
  -W \
  -c "SELECT current_user, current_database();"
!

Ne jamais utiliser trust pour le rôle applicatif et ne jamais appliquer chmod 777 au répertoire de sauvegarde. Le port 5432 ne doit pas écouter sur 0.0.0.0 ni sur l’IP publique.

09 / EDGE

Caddy centralise le Web, l’API et HTTPS

L’image Web est construite en deux étapes : Vite compile la SPA avec l’URL publique de l’API, puis Caddy sert les fichiers de /srv et reverse-proxy les routes backend.

Chemin publicDestinationComportement
/SPA React dans CaddyFallback index.html pour le routing client
/api/*api:8080Reverse-proxy sans modifier le chemin
/uploads/*api:8080Médias persistés dans api-uploads
POST /payment-status.phpIPN PayDunyaRéécrit vers /api/v1/payments/paydunya/ipn
Caddyfile · configuration de référence
{
  email {$TLS_EMAIL}
}

# Cette redirection exige un DNS www pointant vers le VPS.
www.{$DOMAIN} {
  redir https://{$DOMAIN}{uri} 308
}

{$DOMAIN} {
  encode zstd gzip

  @backend path /api/* /uploads/*
  handle @backend {
    reverse_proxy api:8080
  }

  # PayDunya appelle cet endpoint en POST serveur-à-serveur.
  @paydunyaIpn {
    path /payment-status.php
    method POST
  }
  handle @paydunyaIpn {
    rewrite * /api/v1/payments/paydunya/ipn
    reverse_proxy api:8080
  }

  handle {
    root * /srv
    try_files {path} /index.html
    file_server
  }
}
i

VITE_API_BASE_URL est injectée pendant le build Vite sous la forme https://DOMAIN/api/v1. Un changement de domaine nécessite donc un rebuild, pas seulement un redémarrage de Caddy.

10 / DOCKER

Compose de production à deux services

Le Compose cible est lancé depuis SendProColis-Web. Il construit Caddy et l’API, conserve leurs données persistantes et monte le socket natif dans l’API. PostgreSQL n’est plus un service Compose.

Sauvegarder la configuration actuelle

Shell · fichiers de rollback
cd ~/procolis/SendProColis-Web

cp -a docker-compose.yml \
  "$BACKUP_DIR/docker-compose.yml.before-native-postgres"

cp -a .env \
  "$BACKUP_DIR/env.before-native-postgres"

chmod 600 "$BACKUP_DIR/env.before-native-postgres"

# Conserver aussi la stack API autonome si elle porte la source historique.
cp -a ../SendProColis-Api/docker-compose.yml \
  "$BACKUP_DIR/api-compose.before-native-postgres.yml"
cp -a ../SendProColis-Api/.env \
  "$BACKUP_DIR/api-env.before-native-postgres"
chmod 600 "$BACKUP_DIR/api-env.before-native-postgres"

Configuration cible

SendProColis-Web/docker-compose.yml
# Production : Caddy + API Docker, PostgreSQL 16 natif Debian.
services:
  caddy:
    build:
      context: .
      dockerfile: Dockerfile
      args:
        VITE_API_BASE_URL: https://${DOMAIN}/api/v1
    image: sendprocolis-web:latest
    container_name: sendprocolis-caddy
    restart: unless-stopped
    ports:
      - "80:80"
      - "443:443"
    environment:
      DOMAIN: ${DOMAIN:?DOMAIN doit etre defini}
      TLS_EMAIL: ${TLS_EMAIL:?TLS_EMAIL doit etre defini}
    volumes:
      - caddy-data:/data
      - caddy-config:/config
    depends_on:
      - api

  api:
    build:
      context: ../SendProColis-Api
    image: sendprocolis-api:latest
    container_name: sendprocolis-api
    restart: unless-stopped
    environment:
      NODE_ENV: production
      PORT: 8080
      DATABASE_URL: ${DATABASE_URL:?DATABASE_URL doit etre definie}
      JWT_ACCESS_SECRET: ${JWT_ACCESS_SECRET:?JWT_ACCESS_SECRET requis}
      JWT_REFRESH_SECRET: ${JWT_REFRESH_SECRET:?JWT_REFRESH_SECRET requis}
      JWT_ACCESS_EXPIRES_IN: 15m
      JWT_REFRESH_EXPIRES_IN: 30d
      OTP_EXPIRES_MINUTES: 10
      UPLOAD_STORAGE: local
      UPLOAD_LOCAL_DIR: uploads
      PUBLIC_BASE_URL: https://${DOMAIN}
      CORS_ORIGIN: https://${DOMAIN}
      LOG_LEVEL: info
      RATE_LIMIT_WINDOW_MS: 900000
      RATE_LIMIT_MAX: 300
      AUTH_RATE_LIMIT_MAX: 30
      BREVO_API_KEY: ${BREVO_API_KEY:-}
      BREVO_SENDER_EMAIL: ${BREVO_SENDER_EMAIL:-}
      BREVO_SENDER_NAME: ${BREVO_SENDER_NAME:-PRO COLIS}
      BREVO_SMS_SENDER: ${BREVO_SMS_SENDER:-ProColis}
      PAYDUNYA_MODE: ${PAYDUNYA_MODE:-test}
      PAYDUNYA_MASTER_KEY: ${PAYDUNYA_MASTER_KEY:-}
      PAYDUNYA_PRIVATE_KEY: ${PAYDUNYA_PRIVATE_KEY:-}
      PAYDUNYA_TOKEN: ${PAYDUNYA_TOKEN:-}
    volumes:
      - api-uploads:/app/uploads

      # Le socket natif évite tout port PostgreSQL sur le réseau Docker.
      - type: bind
        source: /var/run/postgresql
        target: /var/run/postgresql
    # Aucun ports: l'API est joignable uniquement par Caddy.

volumes:
  caddy-data:
  caddy-config:
  api-uploads:

Par rapport à l’ancienne stack, supprimer impérativement :

  • Le service Compose postgres et son healthcheck.
  • Le bloc api.depends_on.postgres.
  • Le volume top-level postgres-data.
  • L’URL contenant l’hôte Docker postgres:5432.
  • Tout mapping public du port API ou du port PostgreSQL.
Shell · validation sans afficher les secrets
cd ~/procolis/SendProColis-Web
docker compose config -q
11 / START

Construire et démarrer la stack

La commande complète reconstruit les images et remplace les conteneurs existants. Les migrations Prisma sont exécutées automatiquement par l’image API avant le démarrage du serveur Node.js.

!

Pour une migration depuis PostgreSQL Docker, ne démarrer la nouvelle API qu’après le dump, la restauration et les comparaisons de la section Transition. Sur une installation neuve, la commande ci-dessous peut être exécutée dès que la base native est prête.

Shell · build et lancement
cd ~/procolis/SendProColis-Web

docker compose config -q
docker compose up -d --build --force-recreate

docker compose ps
docker compose logs --tail=150 caddy api
Shell · recette initiale
curl -fsS https://sendprocolis.exemple.com/api/v1/health

docker compose exec api npx prisma migrate status

docker compose exec api \
  sh -lc 'test -S /var/run/postgresql/.s.PGSQL.5432 && echo "Socket PostgreSQL OK"'
✓

L’API n’a pas de port hôte dans la stack cible. Tous les tests HTTP externes passent par Caddy et le domaine HTTPS, ce qui valide simultanément DNS, TLS, routage et application.

12 / CUTOVER

Geler, exporter, restaurer

Cette phase ouvre la maintenance. L’ancienne base reste disponible en lecture pour les contrôles, mais l’API est arrêtée afin de figer les écritures.

1. Arrêt applicatif et dump final

Shell · source Docker
cd ~/procolis/SendProColis-Api

docker compose stop api

docker exec procolis-node-postgres \
  psql -U procolis -d procolis -Atc "
SELECT count(*)
FROM pg_stat_activity
WHERE datname = 'procolis'
  AND pid <> pg_backend_pid();
"

FINAL_BACKUP="$BACKUP_DIR/procolis-final-$(date +%Y%m%d-%H%M%S).dump"

docker exec procolis-node-postgres \
  pg_dump -U procolis -d procolis \
  --format=custom \
  --verbose \
  > "$FINAL_BACKUP"

test -s "$FINAL_BACKUP"
docker exec -i procolis-node-postgres pg_restore --list \
  < "$FINAL_BACKUP" \
  > /dev/null

chmod 600 "$FINAL_BACKUP"
sha256sum "$FINAL_BACKUP"

2. Restauration transactionnelle

Confirmer que la destination ne contient encore aucune table applicative :

Shell · précontrôle destination
sudo -u postgres psql -d procolis -Atc "
SELECT count(*)
FROM pg_catalog.pg_tables
WHERE schemaname = 'public';
"

Le résultat attendu est 0.

i

Le répertoire de sauvegarde est volontairement en mode 700. Le dump est donc transmis à pg_restore par l’entrée standard : le shell debian ouvre le fichier, puis l’utilisateur postgres reçoit son contenu sans avoir accès au répertoire.

Shell · destination native
RESTORE_LOG="$BACKUP_DIR/restore-$(date +%Y%m%d-%H%M%S).log"
set -o pipefail

sudo -u postgres pg_restore \
  --dbname=procolis \
  --no-owner \
  --role=procolis \
  --exit-on-error \
  --single-transaction \
  --verbose \
  < "$FINAL_BACKUP" \
  2>&1 | tee "$RESTORE_LOG"

RESTORE_STATUS=$?
echo "Code de restauration : $RESTORE_STATUS"
!

Le code doit être 0. Tout autre code impose l’arrêt immédiat de la procédure. Grâce à --single-transaction, une erreur annule la restauration en cours.

Shell · statistiques
sudo -u postgres psql -d procolis -c "ANALYZE;"
13 / GO-LIVE

Comparer avant de basculer

La source Docker reste active mais l’API est arrêtée. Comparer des tables métier critiques, vérifier Prisma, puis seulement arrêter le moteur source.

Shell · requête de contrôle
CHECK_SQL='
SELECT '\''User'\'' AS table_name, count(*) FROM public."User"
UNION ALL
SELECT '\''Parcel'\'', count(*) FROM public."Parcel"
UNION ALL
SELECT '\''Payment'\'', count(*) FROM public."Payment"
UNION ALL
SELECT '\''WalletTransaction'\'', count(*) FROM public."WalletTransaction"
UNION ALL
SELECT '\''_prisma_migrations'\'', count(*) FROM public."_prisma_migrations"
ORDER BY 1;
'

docker exec procolis-node-postgres \
  psql -U procolis -d procolis -Atc "$CHECK_SQL" \
  | tee "$BACKUP_DIR/source-counts.txt"

sudo -u postgres \
  psql -d procolis -Atc "$CHECK_SQL" \
  | tee "$BACKUP_DIR/native-counts.txt"

diff -u \
  "$BACKUP_DIR/source-counts.txt" \
  "$BACKUP_DIR/native-counts.txt"

Si diff ne retourne rien, arrêter la source puis lancer la stack de production cible depuis le dépôt Web :

Shell · bascule
docker stop procolis-node-postgres

cd ~/procolis/SendProColis-Web
docker compose up -d --build --force-recreate

docker compose ps
docker compose logs --tail=150 caddy api
Shell · tests post-déploiement
docker compose exec api \
  sh -lc 'test -S /var/run/postgresql/.s.PGSQL.5432 && echo "Socket PostgreSQL OK"'

docker compose exec api npx prisma migrate status

curl -fsS https://sendprocolis.exemple.com/api/v1/health

sudo systemctl is-active postgresql
sudo ss -ltnp | grep ':5432' || true
  • Le conteneur API est Up et ses logs ne contiennent aucune erreur Prisma.
  • Le socket .s.PGSQL.5432 est visible dans le conteneur.
  • prisma migrate status confirme que le schéma est à jour.
  • L’endpoint /health répond avec un code HTTP 2xx.
  • Le port 5432 n’écoute pas sur l’interface publique.
14 / UPDATE

Mettre à jour sans conserver d’anciens conteneurs

Tirer les deux dépôts, reconstruire les images puis forcer la recréation. Cette dernière étape est indispensable pour que les conteneurs utilisent réellement les nouvelles images.

Shell · déploiement d’une version
cd ~/procolis/SendProColis-Web
git pull --ff-only

cd ~/procolis/SendProColis-Api
git pull --ff-only

cd ~/procolis/SendProColis-Web
docker compose config -q
docker compose up -d --build --force-recreate

docker compose ps
docker compose logs --tail=150 caddy api
curl -fsS https://sendprocolis.exemple.com/api/v1/health
i

Le démarrage de l’image API lance npx prisma migrate deploy avant Node.js. Une migration défectueuse fait donc échouer le conteneur et doit être diagnostiquée dans docker compose logs api avant toute autre action.

Shell · nettoyage après validation
# Exécuter uniquement après avoir validé la nouvelle version.
docker image prune -f
!

Ne pas associer ce nettoyage à docker volume prune. Les volumes Caddy et uploads portent des données persistantes et ne doivent jamais être supprimés par une commande de maintenance générique.

15 / RUN

Sauvegarder et superviser toute la stack

PostgreSQL est piloté par systemd ; Caddy et l’API par Compose. La stratégie de sauvegarde couvre séparément la base native, les uploads et la configuration du VPS.

Commandes d’exploitation

Besoin Commande

16 / APP

Gérer les uploads et l’administration initiale

Les médias sont stockés dans le volume Docker api-uploads, tandis que les comptes et configurations fonctionnelles résident dans PostgreSQL natif.

Cycle de vie des médias

Client HTTPS → Caddy /uploads → API /app/uploads → api-uploads
  • UPLOAD_STORAGE=local et UPLOAD_LOCAL_DIR=uploads restent configurés dans l’API.
  • PUBLIC_BASE_URL=https://DOMAIN permet de générer des URLs publiques correctes.
  • Le volume api-uploads doit être sauvegardé avant toute suppression ou recréation destructive.
  • Les routes /uploads/* doivent continuer à être transmises par Caddy à l’API.

Après la reprise des écritures sur PostgreSQL natif, revenir au volume Docker ferait perdre ces nouvelles données. Dans ce cas, préparer une migration inverse à partir d’un nouveau dump ; ne pas exécuter le bloc ci-dessus.

Conserver le conteneur source arrêté, le volume postgres-data et le dump final pendant la période de validation. Ne jamais lancer docker compose down -v pendant cette période.
